# chatgpt-plus-price-monitor

监控 [priceai.cc](https://priceai.cc/products/chatgpt-plus) 上 ChatGPT Plus 的报价，
当**最便宜的可信报价**低于阈值时通过 Telegram 通知。

零第三方依赖，只用 Go 标准库。

## 用法

```sh
go build -o chatgpt-plus-price-monitor .
```

先看看现在什么价。**不设环境变量时只打印日志，不发通知**：

```sh
./chatgpt-plus-price-monitor -i 0 -v
```

```
未设置 TELEGRAM_BOT_TOKEN / TELEGRAM_CHAT_ID，只打印结果，不发送通知
最便宜的可信报价 100.94 元（参考价位 121.54，地板线 60.77，剔除 0 条），阈值 10.00 -> 未达成
  1. 100.94 元 | Ai小卖部 | 【自营】gpt plus （upi） 未接码 | 质保一个月...
  2. 101.97 元 | Ai俱乐部 | GPT plus （8.10号菲区正价开通的Gmail成品号）
  ...
```

用它确认 `--threshold` 定在合理位置，再配通知：

1. 找 [@BotFather](https://t.me/BotFather) 发 `/newbot`，拿到形如 `123456:ABC-DEF...` 的 token；
2. 给你的 bot 发一条消息，然后访问
   `https://api.telegram.org/bot<TOKEN>/getUpdates`，从返回里找到 `chat.id`；
3. 两个都设置好，就会开始发通知：

```sh
export TELEGRAM_BOT_TOKEN=123456:ABC-DEF...
export TELEGRAM_CHAT_ID=123456789
./chatgpt-plus-price-monitor -i 30m -n 5 -t 10
```

凭据只从环境变量读，没做成命令行选项：写在命令行上同机器的其他人 `ps` 就能看到。

## 选项

| 选项 | 默认值 | 说明 |
| --- | --- | --- |
| `-t, --threshold` | `10` | 最便宜的可信报价低于该价格（元）时通知 |
| `-i, --interval` | `30m` | 轮询间隔，`0` 表示只检查一次就退出 |
| `-m, --min-price` | `0` | 排除低于该价格的报价，用于滤掉日抛等另一档商品 |
| `-s, --sample` | `30` | 取多少条报价作为参考价位的样本 |
| `--floor-ratio` | `0.5` | 低于 参考价位×该比例 的报价视为异常规格剔除 |
| `-n, --top` | `5` | 通知里列出最便宜的 N 条 |
| `--cooldown` | `24h` | 持续低于阈值时的重复提醒间隔，`0` 表示只提醒一次 |
| `--no-rebound` | | 价格回升到阈值之上时不通知 |
| `--fail-threshold` | `3` | 连续抓取失败 N 次后告警，`0` 表示关闭 |
| `--timeout` | `30s` | 单次 HTTP 请求超时 |
| `-v, --verbose` | | 打印每条报价的店铺和标题 |

## 数据来源

直接调页面背后的接口，不解析 HTML：

```
GET https://priceai.cc/api/products/chatgpt-plus/offers?limit=<top>&offset=0
```

这个接口**默认按价格升序返回**，所以 `offset=0&limit=N` 拿到的就是最便宜的 N 条，
也正是页面上显示的前 N 条，本地不需要再排序。

用到的字段是 `price`、`currency`、`sourceStoreName`、`sourceTitle`、`url`。
通知里会把价格做成可点的链接，收到就能直接跳去下单。

接口返回条数少于 `--sample`、或币种不是 CNY 时直接报错退出（exit code 1）。
不完整或不可比的样本很可能凑巧低于阈值而误报，宁可报错。

## 怎么判断"真便宜"

卖家常把日抛、加购项、拼车之类的东西挂在同一个商品下，价格只有正常月卡的零头。
直接看均价或最低价都会被这些报价带偏：

| 前 5 个报价 | 均价 | 均价规则 | 期望 |
| --- | --- | --- | --- |
| 2, 11, 11.5, 12, 11 | 9.5 | 通知 ❌ | 不通知，`2` 不是一份月卡 |
| 9, 11, 11.5, 12, 11 | 10.9 | 不通知 ❌ | 通知，`9` 是真便宜 |

所以改成两步筛选：

1. **`--min-price` 排除掉整档不想要的商品**（见下节）
2. 取剩下报价的**中位数**作为参考价位（中位数不受极端值影响，均值会）
3. 地板线 = 参考价位 × `--floor-ratio`（默认 0.5）
4. 低于地板线的报价当作**别的规格**剔除
5. 在剩下的里取最便宜的一条，和 `--threshold` 比

顺序很重要：先排除掉另一档商品，中位数才落在你真正关心的价位上。

上面两种情况参考价位都是 11，地板线 5.5：`2` 被剔除后最低是 11，不通知；
`9` 保留下来，低于阈值，通知。`2, 9, 11, 11.5, 12` 这种也能正确处理 ——
剔除 2 之后仍然发现 9 这个真实低价。

`--sample` 要比 `--top` 大不少（默认 30）。如果只看最便宜的 5 条，而这 5 条恰好
全是日抛，中位数本身就是错的，什么也剔除不掉。样本大一些才能覆盖到真实价位。

## 为什么需要 --min-price

站上的报价是**按商品类别分层的**，不是单一价位加几个异常值。抓 `offset=0` 的
30 条实测：

- 价格 18.69 ~ 27.04 元，挤成一团
- 30/30 条都是「未接码 PLUS 成品号，**质保半小时内首次登录**」，也就是日抛号
- 其中 21 条标题**一字不差**

而月卡（质保 30 天）在 100 元以上。两档商品价格差约 4 倍，中间没有重叠。

统计方法区分不了这两档 —— 日抛那一档内部价格非常整齐，没有任何异常值可剔除。
标题和 `filterTags` 又都是商家自己填的，可以为了曝光乱标。**只有价格档位骗不了人**，
所以用 `--min-price` 划一条线：

```sh
# 只关心月卡，不要日抛
./chatgpt-plus-price-monitor -m 60 -t 100
```

`-i 0 -v` 会把被排除和被剔除的报价分别打出来，据此确定这条线画在哪：

```
  [低价档] 18.69 元 | 奥特曼大表哥 | 【未接码】PLUS成品号...质保半小内首次登录
```

`--floor-ratio` 则用于同一档商品内部的异常值，调小更宽松，调大更严格。

## 通知时机

只在**状态发生变化**时通知，而不是每轮都推：

- 均价从阈值之上跌到之下 → 「降价提醒」
- 持续低于阈值 → 静默，直到超过 `--cooldown`（默认 24 小时）才再提醒一次
- 均价回升到阈值之上 → 「价格回升」，之后恢复静默
- 连续抓取失败 `--fail-threshold` 次 → 「监控异常」，带上原始错误
- 抓取恢复 → 「监控已恢复」

抓取失败告警是为了防止监控静默死掉：接口改版、被限流、网络不通都会让抓取失败，
日志没人看的话，你以为它在盯着，其实早就不工作了。
一轮故障只告警一次；如果告警本身也发不出去，不会记成"已告警"，下一轮会重试。

去重状态只存在内存里，所以要常驻运行才有意义。重启会重新武装：
如果重启时价格仍低于阈值，会再收到一条降价提醒。
`--once` 每次都是全新状态，适合手动看一眼当前价格，不适合挂 cron。
